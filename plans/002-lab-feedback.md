## گام‌های اختصاصی

1. در initLab گروه‌های ساخت/مدل آماده/n و گاما را در بخش «ساخت»، ابزار حرکت/یال را در «تغییر»، و check/hint/clear را در «بررسی» قرار بده. در دسکتاپ ابزار کنار برد، در گوشی details در جریان صفحه؛ DOM را برای هر breakpoint دوباره clone نکن. بررسی: تمام ایستگاه‌ها، ساخت با n و گاما و بارگذاری مدل آماده در تست browser جدید کار کنند.
2. عنوان و مشخصات مدل، notice و نتیجه بررسی را نزدیک برد بیاور. در redraw بخش باز ابزار، مقدار ورودی و فوکوس معتبر حفظ شوند؛ یادداشت‌های موقت RAM باقی بمانند. بررسی: ویرایش یال/انتخاب، تغییر ایستگاه و چند بار redraw، هیچ امتیاز/attempt/session جدید در snapshot نسازند.
3. API اختیاری تشخیص بصری را روی حالت موجود missed/hinted توسعه بده: بی‌پوشش با حلقه و متن، حذف‌پذیر فقط پس از بررسی/درخواست راهنما با نشان مستقل. رنگ مالک، هاشور و انتخاب را بازنویسی نکن. این نشانه‌ها در 3D هم از وضعیت مشترک خوانده شوند؛ داور جدید نساز. با تغییر پاسخ نشانه تشخیص کهنه پاک شود. بررسی: تک‌مالک/چندمالک، پاسخ ناقص، مینیمال غیرمینیمم، درست و WebGL fallback.
4. بازخورد متن نزدیک برد و aria-live یک‌بار اعلام شود. پیش از درخواست بررسی یا راهنما پاسخ یا رأس قابل حذف آشکار نشود. برای آموزش/مسابقه فقط opt-in آینده؛ هیچ reveal خودکار به آن‌ها اضافه نکن. بررسی: baseline هر دو بخش و test عدم leakage.
5. تست browser جدید را از mobile-browser الگوبرداری کن: ساخت، تغییر، بررسی، empty، خطا ورودی، dropdown رو به پایین روی ابزار، keyboard، mobile/desktop و دو تم. شکل‌های جدید را در گزارش antislop توجیه و سپس پیش‌نمایش و PR بده؛ توقف.

## قرارداد مستقل اجرای این فاز

- پروژه گراف‌نامه یک سایت فارسی RTL، استاتیک، بدون بیلد و backend است؛ HTML/CSS و ES modules، قلم محلی Vazirmatn، فرمول KaTeX و ماندگاری localStorage دارد. React یا وابستگی جدید اضافه نکن.
- هدف، پرداخت بصری کارگاه ریاضی است: ENERGY 3 / RHYTHM 2 / MOTION 2. برد نقطه کانونی، فاصله برای تفکیک وظایف، رنگ تاکید فقط برای وضعیت مهم، حرکت کوتاه برای توضیح تغییر.
- پالت روز باغ و مرجان و شب زغال و فیروزه و توکن‌های فعلی حفظ شوند. سطوح کار مات و خوانا؛ شیشه اضافه روی کارت/برد ممنوع. پس‌زمینه جهان گراف و پنجره ناوبری مصوب حفظ شوند.
- همه بردهای تعاملی از `paintGraph` و `attachGraphView` در `assets/js/ui/graph-surface.js` استفاده می‌کنند. `graph-editor.js`، `teaching-board.js` و `model-workbench.js` آداپترند؛ renderer مستقل برای هر تب نساز. انتخاب و هاشور در `vertex-selection.js` و نمای سه‌بعدی در `graph-three.js` است. اشکال تزئینی، برد آموزشی نیستند.
- هیچ شناسه سوال، پاسخ مرجع، قفل APOS، گراف مسئله، سیاست امتیاز، schema یا داده ذخیره‌شده تغییر نکند. آزمایشگاه آزاد و بدون ثبت امتیاز/تلاش است؛ درصد آموزش فقط تکمیل مسیر است.
- قبل از اجرا: `AGENTS.md`، `.agent/README.md`، `.agent/skills/project-workflow/SKILL.md`، `.specify/memory/constitution.md`، این پلن، قرارداد ویژگی مرتبط و اسناد spec/plan/tasks آن را بخوان. قراردادهای فعال: `specs/002-apos-teaching-v11/`، `specs/004-graph-workspace/`، `specs/005-graph-world/` و `specs/006-graph-mobile/`.
- در هر فاز از ui-ux-pro-max برای تصمیم بصری، Graphify برای شناخت کد، Spec Kit برای spec/plan/tasks و antislop در حالت during از طراحی تا اجرا استفاده کن. improve برای بهبود پلن و بازبینی است؛ مسیر execute آن به مجری جدا در worktree نیاز دارد. مهارت مرتبط Three.js را فقط برای کار لازم در سه‌بعدی بخوان. liquid-glass-design بومی iOS است؛ روی وب فقط اصول خوانایی، گروه‌بندی و پرهیز از شیشه تودرتو مرتبط است، API بومی اضافه نکن. سایر مهارت‌ها را متناسب با نیاز واقعی انتخاب کن؛ نصب خودکار نکن.
- Graphify قبل از جست‌وجوی کد: `graphify query "<موضوع همین مرحله>"`؛ برای رابطه از `graphify path` و برای مفهوم از `graphify explain` استفاده کن. نتایج INFERRED را اثبات قطعی ندان. کد محل اشاره‌شده را تطبیق بده؛ گراف موجود به‌تنهایی اثبات تازگی همه فایل‌ها نیست. پس از تغییر کد `graphify update .`؛ انتظار خروج موفق و بازسازی گراف را ثبت کن.

## مراحل مشترک و گیت‌ها

1. **آماده‌سازی:** `git status --short --branch` و `git rev-parse --short HEAD`. تغییرات دیگران را حفظ کن. `git diff --stat 59388a0..HEAD -- <فایل‌های محدوده>` و تطبیق excerptها؛ تغییرات پیش‌نیاز مصوب طبیعی‌اند، تغییر نامرتبط نیازمند بازبینی پلن است. روی شاخه `codex/<نام فاز>` کار کن، نه main. اگر checkout اصلی در حال استفاده است، worktree مدیریت‌شده مناسب بساز.
2. **ثبت قرارداد قبل از اجرا:** در پوشه spec همین فاز، spec/plan/tasks را با رفتارهای این سند و معیارهای پذیرش بنویس. پیش از تغییر محصول، baseline آزمون‌های جدول را اجرا کن. انتظار: exit 0؛ خطای baseline را از خطای معرفی‌شده جدا کن.
3. **اجرای گام‌های اختصاصی:** فقط فایل‌های محدوده؛ الگوی فعلی `document.createElement`، `textContent`، `renderTextMath`، `destroy()` و توکن CSS حفظ شود. UI را با اسکریپت جایگزینی رشته در سورس وصله نکن. پس از هر گام آزمون مشخص‌شده را اجرا کن؛ انتظار exit 0 و بدون استثنای runtime.
4. **بررسی مرورگر:** روز/شب در عرض‌های 320،390،768،1280؛ فارسی و فرمول، متن بلند و زوم مرورگر 200٪. عدم سرریز صفحه را با `document.documentElement.scrollWidth <= innerWidth` بسنج؛ اسکرول داخل برد بزرگ مجاز است. keyboard Tab/Enter/Space/Escape، فوکوس نمایان، هدف لمس حداقل44px و فاصله حداقل8px بررسی شود. متن عادی حداقل4.5:1 و بزرگ3:1؛ عدد اندازه‌گیری‌شده را ثبت کن، نه فرض.
5. **پیش‌نمایش:** `python3 -m http.server 8771 --bind 127.0.0.1` از checkout فاز یا پورت آزاد دیگر. نشانی هر hash تغییرکرده با query کامیت، تصاویر روز/شب و گوشی/دسکتاپ را در Codex باز کن؛ پاسخ HTTP و تطبیق کد با شاخه را تایید کن. سرور را برای بازبینی روشن نگه دار. وضعیت‌های خالی، خطا، درحال آماده‌سازی و WebGL ناموجود را در صورت ارتباط نشان بده.
6. **گیت تحویل:** آزمون‌های موجود و جدید با exit 0، کنسول بدون خطای معرفی‌شده، `git diff --check` بدون خروجی و diff محدود به فهرست مجاز. مشخص کن کدام مرورگر/دستگاه واقعا تست شده است. تست خودکار معادل گوشی فیزیکی نیست. antislop را حین تصمیم و پیاده‌سازی اعمال کن؛ ایرادهای داخل محدوده را همان زمان اصلاح کن. پیش از تحویل Delivery Gate با همه R01..R40 و C1..C5، دلیل تکنیک‌ها و شواهد واقعی ثبت شود. در پایان بگو آیا پیشنهاد دیگری باقی است؛ پیشنهاد خارج محدوده بدون تایید اجرا نشود.
7. **توقف:** PR متمرکز برای همین فاز بساز و URL را همراه پیش‌نمایش و گزارش بده؛ PR را به چت attach کن. وضعیت را «آماده بازبینی» ثبت کن. بدون تایید صریح کاربر merge، انتقال به main یا شروع فاز بعد ممنوع است. تایید مرج یک فاز، مجوز شروع فاز بعد نیست. پس از مجوز مرج، شاخه اصلی پوشه اصلی را بدون حذف کار محلی همگام کن.

## معیار پذیرش مشترک

- تمام فرمان‌های جدول exit 0؛ تست جدید رفتار واقعی را بررسی کند، نه فقط وجود class یا متن.
- hashها، دکمه‌های اصلی و نام‌های دسترس‌پذیر قبلی حفظ یا migration تست‌ها در PR توضیح داده شود؛ تست را برای پنهان‌کردن رگرسیون ضعیف نکن.
- 2D/3D، انتخاب با mouse/touch/keyboard، کشیدن پس از چرخش، پوشش تک‌مالک/چندمالک، حفظ زوم پس از redraw و تعویض نما سالم بمانند.
- motion off/low و prefers-reduced-motion مقدم‌اند. حرکت طولانی با کنترل موجود توقف داشته باشد؛ حرکت به پیش‌نیاز ثبت پاسخ تبدیل نشود.
- هیچ فایل داده/دامنه/ذخیره‌ساز خارج از محدوده تغییر نکند. داده مرورگر شخصی پاک نشود؛ از پروفایل موقت تست استفاده کن.
- `plans/README.md` با شواهد واقعی و وضعیت فاز به‌روز شود. تعداد تست‌ها پیشاپیش جعل نشود.

## شرایط توقف و نگهداری

اگر رفع مشکل به تغییر schema، منطق امتیاز، معیار عبور APOS، کتابخانه جدید، renderer موازی یا فایل خارج محدوده نیاز داشت، توقف و علت را گزارش کن. اگر یک بررسی پس از دو تلاش معقول همچنان شکست خورد، همان بخش را مسدود اعلام کن؛ نتایج موفق مستقل را نگه دار. شماره خط فقط نشانی اولیه است؛ نماد و excerpt ملاک تطبیق‌اند.

بازبین باید حفظ قرارداد آداپترها، پاک‌سازی event/observer، focus و وضعیت موقت را بررسی کند. برای آینده، امکانات مشترک فقط در هسته توسعه یابند و داده و ارزیابی در لایه خود بمانند.
